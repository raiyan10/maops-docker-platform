# v0.6.0 — CI/CD and Release Engineering

Day 6 of the MAOps Docker Platform seven-day portfolio arc. This release
adds a **delivery plane** on top of the unchanged **runtime plane** built
across Days 1–5: automated GitHub Actions CI for every pull request and
every push to `main`, a controlled, tag-triggered release workflow with a
safe non-publishing dry run, and closure of the Day 5 test/harness findings
that automation now makes authoritative. See
[docs/ci-cd.md](../ci-cd.md) for the full delivery-plane design.

## Runtime plane: unchanged

`gateway -> app -> state`, three services, two networks (`edge`,
`backend: internal: true`), one named volume (`state_data`), one
application image, loopback-only host publication via `gateway` — all
exactly as shipped in v0.5.0. Day 6 does not touch `compose.yaml`'s
topology, `docker/app/Dockerfile`'s base images, or any runtime hardening
property. See [docs/architecture.md](../architecture.md) and
[docs/compose-platform.md](../compose-platform.md).

## CI/CD delivery plane (new)

- **`.github/workflows/ci.yml`** — runs on every `pull_request` targeting
  `main` and every `push` to `main`. Two jobs: `quality` (fast, Docker-free
  static checks — `make quality`, now including `workflow-check`) fails
  first and cheaply; `release-policy` (needs `quality`) runs the full
  authoritative `make release-check` — build, image-audit, smoke,
  security-check, compose-test, reliability-check, reproducibility-check,
  SBOM, SBOM validation, vulnerability-policy enforcement, and supply-chain
  validation — against a real Docker Engine already provided by the
  GitHub-hosted Ubuntu runner (no Docker Engine installation step).
- **`.github/workflows/release.yml`** — the controlled release workflow.
  `workflow_dispatch` can be selected against any ref, but this project's
  release contract makes the dry run authoritative on `refs/heads/main`
  only: `scripts/release/check_release_context.py` (invoked with the real
  `--event-name`/`--ref` GitHub context, as an unconditional step run
  *before* the expensive gate below) rejects every other ref — a feature
  branch, `develop`, a tag ref, an empty/malformed ref — with a clear,
  non-zero failure, never a silent skip. Only once that ref check passes
  does the dry run derive the proposed tag from `VERSION`, run the
  identical `make release-check` gate, validate the release notes exist,
  and clearly report `DRY RUN` — it can never create a Git tag, a GitHub
  Release, or publish a container image, main-only or not. Only a real
  `push: tags: v*.*.*` event can publish, and only after every gate passes
  and the tagged commit is independently proven to belong to `main`'s
  history (`git merge-base --is-ancestor`, full clone via
  `fetch-depth: 0`) — a separate event path from the dispatch ref check
  above; a tag push never needs to satisfy it, and a dispatch run never
  needs a version tag.
- **Least privilege**: `ci.yml` runs with `permissions: contents: read`
  workflow-wide — no PR run ever receives a write token or a secret.
  `release.yml` splits `validate` (`contents: read`) from `publish`
  (`contents: write`, only this one job, only reachable on a real tag
  push); `publish` depends on `validate` passing.
- **Action supply-chain security**: every `uses:` reference
  (`actions/checkout`, `actions/setup-python`, `actions/upload-artifact`,
  `actions/download-artifact`) is pinned to an immutable, independently
  resolved full commit SHA via the GitHub API (`gh api
  repos/<org>/<repo>/releases/latest` → `gh api .../git/refs/tags/<tag>`),
  with the corresponding trusted release tag named in a trailing comment.
  No floating `@main`/`@v4` reference anywhere.
- **`pull_request_target` is never used** — PR validation runs entirely
  under `pull_request`, with the base repository's own read-only token and
  no secrets, so a malicious PR branch can never exfiltrate a write-scoped
  token or a secret via CI.
- **Concurrency**: `ci.yml` cancels an obsolete run for the same PR/ref
  (`cancel-in-progress: true`) so stale commits don't consume runner time.
  `release.yml` deliberately does **not** cancel an in-flight run
  (`cancel-in-progress: false`) — interrupting a release mid-publish is
  exactly the kind of half-finished state this project's "no manufactured
  PASS, no silent partial state" philosophy rules out.
- **Artifacts**: the release image's SPDX SBOM and Trivy JSON
  vulnerability report are uploaded from a successful `release-policy`
  (`ci.yml`) or `validate` (`release.yml`) run, retained 7 days. A failed
  gate never gets to the upload step — artifact upload can never disguise
  a failed gate as green.
- **Repository-owned validation, not hand-maintained YAML logic**:
  `scripts/ci/check_workflows.py` (`make workflow-check`, part of `make
  quality`/`make release-check`) statically enforces the workflow-security
  invariants above against the committed `.github/workflows/*.yml` files
  themselves — required files exist, no `pull_request_target`, CI
  permissions are read-only, release write permission is narrowly scoped,
  every `uses:` is a full SHA, no `continue-on-error`/`|| true` around a
  required gate, required triggers are present, the release tag pattern
  exists, the manual dispatch path cannot publish, no registry-publish
  command appears, and no Day 7+ tooling (Cosign, SLSA, Kubernetes, Helm,
  Argo CD, Prometheus, Grafana, OpenTelemetry, Terraform, Ansible) has
  leaked in. `scripts/release/check_release_context.py` independently
  validates `VERSION`/tag format, tag-vs-`VERSION` equality, release-notes
  presence, main-history ancestry, and — the authoritative enforcement of
  the main-only `workflow_dispatch` dry-run contract — that a manual
  dispatch's ref is exactly `refs/heads/main` — pure, Docker-free logic
  with a thin, separately swappable `git` adapter at the one place real
  git is needed.
- **`make release-check` remains the single authoritative local contract**:
  a developer running `make release-check` locally exercises substantially
  the same policy CI enforces — CI orchestrates this project's existing
  validation, it does not reimplement it in workflow YAML.

## Day 5 findings closed in Day 6

Automated gates are now authoritative, so the Day 5 final adjudication's
carried-forward test/harness debt (3 Medium + 6 Low) was closed before
trusting them in CI:

- **M-A** — `with_memory_shrink_restored`'s memory-restore step is now a
  first-class **verified** invariant: after `docker update` restores the
  original memory limit, the container's real `HostConfig` is
  re-`docker inspect`ed and compared against the captured original values.
  A failed restore command, or a restore that reports success but didn't
  actually take effect, both raise `ReliabilityError` — `reliability-check`
  now **fails**, never merely warns to `stderr`.
- **M-B** — a new, fast, Docker-free `tests/test_server.py::StateTimeoutTests`
  proves `app`'s own inner-hop `state_dependency_timeout_seconds` converts
  a slow `state` response into a controlled `503`, mirroring
  `tests/test_gateway_server.py::UpstreamTimeoutTests` for the outer hop.
  The real-Docker A-6 proof in `reliability_check.py` remains the
  authoritative runtime evidence; this closes the regression-speed gap.
- **M-C** — `tests/test_check_compose.py` (new) gives
  `check_resource_limits`/`check_restart_policy`/`check_stop_grace_period`
  and their `_parse_cpus`/`_parse_bytes`/`_parse_duration_seconds` helpers
  their first persisted unit-test coverage, including the adversarial
  cases the Day 5 reviews manually verified but never committed
  (malformed retry counts, Go-duration-string parsing, boundary
  nanosecond/second disambiguation, the `bool`-as-`int` trap).
- **L (health-timeout)** — `reliability_check.py`'s `inner_governed`
  assertion is tightened from a loose `>= inner_timeout * 0.5` lower bound
  to a tight `[inner_timeout * 0.75, inner_timeout * 1.25]` band, still
  comfortably wide of the ~1.75% jitter the health-timeout review measured
  across five real trials.
- **L (resource-restart)** — `check_compose.py`'s structural
  `check_resource_limits()` now requires **exact** equality against the
  approved platform resource contract (not merely "not above target"),
  matching how `reliability_check.py`'s real-Docker
  `check_resource_limits_applied()` already compares — a too-low value is
  now caught at the cheapest gate, not only at real Docker runtime.
- **L (failure-recovery)** — `docs/reliability.md` now explicitly
  distinguishes `RestartCount`'s two behaviors: cumulative across
  *automatic* restart-policy attempts within one continuous container run,
  but reset to `0` by an *explicit* `docker start`/`docker compose start`
  — scoped honestly to this project's own verified Docker install, not
  claimed as a universal `dockerd` guarantee.
  `tests/test_reliability_check.py::SigtermHandlingTests` (new) gives the
  identical `_TerminatedError`/`_install_sigterm_handler()` mechanism
  `compose_integration.py` already had a test for its own Docker-free
  regression coverage in `reliability_check.py` too.
- **L (test-adversarial)** — boundary-inclusive-accept tests for each
  timeout field's `MAX_*` constant (both `app/` and `gateway/`
  `platform_config.py`), and `-Infinity` rejection tests added to
  `tests/test_gateway_platform_config.py` for symmetry with
  `tests/test_app_platform_config.py`.

The seven Day 4 carried-forward findings this Day 6 scope did not touch
(the `image_audit.py` base-digest tautology, its missing unit tests, its
`app/`-only source-immutability probe scope, `check_trivy_report.py`'s
malformed-shape/severity-case gaps, `check_dockerfile.py`'s untested
branches, and the reproducibility manifest's untested uid/gid axis) remain
open, at their previously adjudicated severity, per `.claude/CLAUDE.md`'s
instruction not to turn a later day into an earlier day's cleanup sprint.

## Scope boundaries (explicitly not this release)

- **No container registry publication** — no `docker login`, no `docker
  push`, no GHCR/Docker Hub/ECR/ACR configuration, no registry
  credentials anywhere in this repository. The GitHub Release (with its
  attached SBOM/vulnerability-report/checksum evidence) is this release's
  entire delivery destination; the application container image itself is
  not published anywhere beyond the local Docker daemon that built it.
- **No Day 7+ tooling** — no Cosign, no SLSA/in-toto provenance
  attestation, no multi-platform image publication, no Kubernetes, no
  Helm, no Argo CD, no Prometheus/Grafana/OpenTelemetry, no Terraform, no
  Ansible.
- **Runtime architecture unchanged** — still exactly `gateway -> app ->
  state`, three services, two networks, one named volume, one application
  image. No new runtime service was added for the delivery plane.
- **Release immutability** — the workflow never force-pushes, moves, or
  rewrites a tag, and never overwrites an existing GitHub Release
  (`--clobber` is never used). If a release for the target tag already
  exists, the workflow fails safely rather than silently mutating
  published evidence.
