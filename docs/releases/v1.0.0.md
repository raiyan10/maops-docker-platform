# v1.0.0 — Final Hardening and Production Readiness (release candidate)

**This document describes release-candidate preparation, not a completed
release.** As of this writing, `v1.0.0` has not been tagged and no
GitHub Release has been created — that follows only after independent
engineering review of this Day 7 work, exactly as `v0.6.0` did. This
notes file exists now because `scripts/release/check_release_context.py`
requires it to exist before any future dry run or real tag event for
`v1.0.0` can validate.

Day 7 of the MAOps Docker Platform seven-day portfolio arc — the final
day. This release is deliberately **not** a runtime redesign: it turns
the platform Days 1–6 already built into an independently verifiable
v1.0.0 candidate by closing three carried-forward Medium findings,
materially improving a fourth still-open historical finding, adjudicating
every other surviving Low/Medium finding from the project's own
engineering-review history, and extending the production-readiness
contract to cover all of it.

## The platform, Day 1 through Day 7

- **Secure, non-root, shellless runtime** (Day 1, hardened Day 4): a
  single Python-stdlib application image runs as UID/GID `10001:10001`,
  never root, with `no-new-privileges`, all Linux capabilities dropped,
  and a read-only root filesystem. The final runtime stage is Distroless
  (`gcr.io/distroless/python3-debian13:nonroot`, digest-pinned) — no
  shell, no package manager, no `pip`/`setuptools` — proven by real
  attempted-exec failures against the running container, not merely
  absence-of-binary heuristics. Application source is root-owned and
  genuinely not writable by the runtime UID, independent of Compose's
  own `read_only: true`.
- **One image, three runtime roles, exactly three services** (Day 2–3):
  a single built image runs as `gateway`, `app`, or `state` depending on
  the `command:` Compose selects. `gateway -> app -> state`, with
  `gateway` the sole loopback-published service (`127.0.0.1:8080`); `app`
  and `state` are never host-published. Two explicit Compose networks —
  `edge` (`gateway`+`app`) and `backend` (`app`+`state`, `internal:
  true`) — mean `gateway` and `state` share no network at all, proven by
  a real failed-connection attempt, not merely Compose config.
- **Persistence** (Day 3): a durably persisted monotonic counter lives in
  `state` under the named `state_data` Compose volume, surviving
  container recreation.
- **Centralized, non-secret configuration** (Day 3): `config/
  platform.json`, Compose-mounted read-only into all three services.
- **Health, reliability, and resource controls** (Day 5): `/healthz`
  (liveness) never calls a dependency, on any of the three services;
  `/readyz` is honestly chained. An explicit two-hop timeout-budget
  hierarchy (`state_dependency_timeout_seconds` <
  `gateway_upstream_timeout_seconds` by at least
  `timeout_safety_margin_seconds`) is validated at config-load time,
  closing Day 3 finding A-6. CPU (0.5), memory (128 MiB), and PID (64)
  limits, plus a bounded `on-failure:3` restart policy and a 10s
  `stop_grace_period`, are applied to real containers and proven against
  real Docker behavior: a real `docker pause` on `state` (bounded
  controlled failure, automatic recovery), a real kernel-initiated
  OOM-kill (genuine `SIGKILL`, deliberately not `docker kill`/`stop` —
  both are exempted from the restart-policy engine) with automatic,
  bounded restart and persisted-state survival, and a real
  intentional-stop-does-not-auto-restart proof.
- **Deterministic, reproducible builds** (Day 4): a BuildKit/buildx
  release build, `SOURCE_DATE_EPOCH`-normalized, verified byte-identical
  (exact image-ID match) across two independent `--no-cache` builds.
- **Supply-chain evidence** (Day 4, CI-enforced Day 6): a real SPDX SBOM
  (Syft) and a real vulnerability report (Trivy) for the exact release
  image, both scanners pinned by exact digest, neither ever given the
  Docker socket — scanning a `docker save` archive, never the live
  daemon. Explicit vulnerability policy: zero Critical, zero fixable
  High, enforced honestly (no `.trivyignore`, no severity rewrite).
- **CI/CD and controlled release engineering** (Day 6): GitHub Actions CI
  on every pull request and push to `main` (`make quality` then the full
  `make release-check`); a safe, non-publishing `workflow_dispatch` dry
  run authoritative only on `main`; real tag-triggered (`push: tags:
  v*.*.*`) GitHub Release publication, gated on the tagged commit
  genuinely belonging to `main`'s history; least-privilege permissions
  split by job; every GitHub Action pinned to a full commit SHA; no
  container registry publication anywhere.
- **Day 7 (this release): production readiness.** See below.

## Day 7: three Medium findings closed

1. **Runtime security-patch lifecycle** — `security/runtime-patches.lock`'s
   emergency `libssl3t64` Debian-security overlay (see
   `docs/build-security.md`) previously had no automated tripwire for its
   own exit condition. `scripts/security/patch_lifecycle_check.py`
   (`make patch-lifecycle-check`) now independently `docker pull`s the
   exact pinned Distroless base (derived from `docker/app/Dockerfile`'s
   own `FROM` text, never a duplicated digest constant), inspects the
   real `libssl3t64` version it currently ships, and — using genuine
   Debian version-comparison semantics — proves whether the overlay is
   still required, now redundant, or has drifted from its own documented
   rationale. As of this writing: the pinned base still ships
   `3.5.6-1~deb13u2`; the overlay remains correctly classified
   **required**.
2. **Release-consumer checksum layout** — the real, already-published
   `v0.6.0` release's `SHA256SUMS` referenced CI workspace-relative
   paths, so a consumer downloading the flat GitHub Release assets could
   not directly run `sha256sum -c SHA256SUMS` (the hashes themselves were
   independently verified correct — a filename/path defect, never a
   checksum-integrity one). `scripts/release/prepare_release_bundle.py`
   (`make release-bundle`) now stages a flat, basename-only bundle and
   independently proves the real, unmodified command succeeds against
   it; `release.yml`'s `publish` job attaches that exact bundle.
3. **Post-restart cgroup-v2 race classifier** — Day 6's retry classifier
   for a known GitHub-runner runc/cgroup-v2 post-restart synchronization
   race only recognized one observed failure signature
   (`cgroup.controllers`). A later real CI run exposed a second,
   closely related variant (`memory.max`). The classifier now accepts
   both, via a deliberately narrow, explicitly enumerated filename
   allowlist plus real path-context/ENOENT-semantics matching — never a
   broad "any cgroup-shaped filename" wildcard, and never a change to the
   bounded retry deadline or the mandatory post-update `HostConfig`
   verification.

## Also materially closed: a Day 4 finding

`scripts/build/image_audit.py`'s cross-check that the built release image
genuinely derives from the pinned Distroless base was partially
tautological — it only asserted the built image's own `RootFS` was
inspectable and non-empty, which could never fail even if the base were
wrong. It now independently pulls the exact pinned base and asserts that
base's own layer list is a genuine ordered prefix of the built image's
layer list — real, previously-absent evidence, with new unit test
coverage.

## Production-readiness contract

`make release-check` remains the single authoritative local/CI
validation contract, extended (not duplicated) to cover: unit tests,
source lint, Dockerfile policy, Compose structural policy, workflow
policy, a deterministic image build, image audit (including the real
base-layer cross-check above), vulnerability policy, SBOM, real Compose
integration, health/readiness, persistence, network isolation,
reliability (real Docker failure/recovery proofs), resource limits,
restart semantics, reproducibility, the runtime security-patch
lifecycle, release-bundle preparation, consumer checksum verification,
release-context validation, and supply-chain evidence generation. See
[docs/production-readiness.md](../production-readiness.md) §4 for the
full mapping.

## Scope boundaries (explicitly not this release)

- No container registry publication, no Kubernetes/Helm/Argo CD, no
  Cosign/SLSA attestation, no service mesh, no observability stack, no
  Terraform/Ansible, no cloud infrastructure or deployment environments,
  no external secrets manager — unchanged from every prior day.
- Runtime architecture unchanged: still exactly `gateway -> app ->
  state`, three services, two networks, one named volume, one
  application image.
- No `v1.0.0` Git tag, no GitHub Release, no image publication — this is
  release-*candidate* preparation only.
